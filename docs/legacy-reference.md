# 旧資料から残す参考（コンセプト・仕組み・画面の流れ）

旧システム（PHP。Git 管理外の `_legacy/`）を、2026-11-20 に読み取りだけで調べ、**新アプリを作り進めるときの参考になる部分だけ**をここに残す。コードは移植しない。実在の社名・地名・連絡先・業種の語は、架空のサイトの方針（[CLAUDE.md](../CLAUDE.md)）に合わないので書かない。
「事実」は旧コードを読んで確かめたこと、「推測」は読んだ範囲からの推測（実行はしていない）。

## 新アプリの現在地との差

新アプリは「求人を探す → 詳細 → 会員登録」と、園の画像管理までを作った。応募から運営の対応までの後半は未着手で、`entries` 表（`db/schema.sql`）に列だけがある。次の 5 点は、その後半を作るときの出発点になる。

## 1. 利用の流れ（紹介型という前提）

- 事実: 求職者が先に「エントリーシート」を登録し、運営の担当者が連絡して求人を紹介する、**人材紹介に近い型**。登録の前に、5 段階の説明ページを見せていた。
  1. エントリーシートを書く → 2. 登録完了メール（マイページ ID 入り）→ 3. 担当者の連絡を待つ（この間の作業は不要）→ 4. 連絡を受ける（求人の詳細・面接日程の案内。待つ間に自分で探して応募もできる）→ 5. 面接。
- 最後に「無料で登録」の案内を置き、登録の手間と費用の不安を先に消していた。
- 新アプリに当てると: 登録後に何が起きるかの画面と文面が無い。5 段階は、画面の順と見出しの下書きになる。

## 2. エントリーシートの意味（応募の設計）

- 事実: 求人 1 件ごとの応募レコードは無い。氏名・フリガナ・生年月日・性別・住所・電話 2 本・メール・希望職種（複数）・希望する施設の種類（複数）・業務経験（あり／なし）・希望先（自由記述）・コメント（200 字まで）を**1 回だけ登録**する。求人詳細から来たときは、見ていた求人の法人名を希望先に引き継ぐ。**求人 ID は保存しない。**
- 流れ: 求人一覧・詳細の入口 → 入力 → 確認画面（入力は持ち回り）→ 登録 → 完了。完了画面で「後日、担当者から連絡」「3 営業日以内に連絡が無ければ電話」「1 週間たっても連絡が無ければ問い合わせ」と、**連絡の期限を約束**していた。
- 事実: 確認の時点で、メール・氏名・カナ・生年月日が一致する既存の登録があると、「既に登録されています。新たに登録しますか」と本人に尋ねる（拒否はしない）。
- 新アプリに当てると: `entries` は `user_id` を NULL にできる（先に登録を許す形）が、求人との結び方・重複の扱い・確認画面は決まっていない。「求人 ID を持たせるか」は設計の判断点。
- 旧の複数選択は、カンマ区切りの 1 列で持ち、検索は `find_in_set` だった。新アプリは中間表か配列を使う（`recruit_*` 表と同じ考え方）。

## 3. 運営の申込者一覧と進捗管理

- 事実: 申込者 1 人ごとに、**独立した 6 つのフラグ**（連絡済・就業済・要注意・辞退・不採用・返信なし）と、それぞれ 200 字までのコメントを持つ。1 つの状態が順に進む方式ではない。`entries` の `contacted` `employed` `caution` `declined` `rejected` `no_response` `flag_comments` がこれに当たる。
- 一覧の絞り込み: ID・氏名・カナ・希望先（部分一致）・希望職種（5 区分から選ぶと、その区分の複数の職種へ展開）・希望する施設の種類・業務経験・連絡状況・アカウントの状態。並びは ID と登録日時の昇順・降順の 4 種。
- 「連絡状況」は 3 択（未連絡／連絡済／対応中）。**「対応中」は保存した値ではなく、フラグから導く状態**（連絡済で、就業済・辞退・不採用がいずれも 0）。一度も更新されていない行に「new」の印、凍結中の行は色を変える。
- 一括操作: 全選択・全解除、凍結（表示を止める）、削除（応募とアカウントを同時に消す）、印刷、CSV。凍結と削除は 2 段階に分かれていた。
- 新アプリに当てると: 列だけがあり、画面・API は無い。**「要注意」は個人への評価ラベルなので、作るときは名称・見せる範囲・記録の扱いを決める**（推測: 論点になる）。CSV は全列（個人情報を含む）を出していたので、新アプリでは出す列を絞る。

## 4. 求人登録フォームの項目構成と選択肢

- 事実: 縦長の 1 画面で、募集職種（5 区分から 1 つ選ぶと他は無効になる排他選択＋自由記入）→ 雇用形態 → 法人名・概要 → 勤務地（エリア・乗り場のチェック）→ 業務経験 → 給与（区分・下限・上限）→ 勤務時間（形態・開始・終了・残業）→ 勤務日 → 業務内容 → 休日 → 保険 → 福利厚生 → 画像、の順。**項目ごとに「備考」欄**を付け、送信後は選択肢のラベル付きで内容を再掲する。
- 保存した求人は**必ず非公開**で始め、運営が一覧で選んで公開・非公開・削除をまとめて行う運用だった。
- 選択肢（旧の定義。新アプリの `recruits` の列で、画面・API には出ていないもの）:

| 列 | 旧の区分 |
|---|---|
| `worktime`（勤務時間の形態。5 種） | 固定・シフト・フレックス・裁量・その他 |
| `workday`（勤務日。9 値） | 月〜日・祝・その他 |
| `dayoff`（休日。4 種） | 完全週休二日・4 週 8 休・4 週 6 休・その他 |
| `benefit`（福利厚生。4 種） | 交通費・資格取得支援・寮／住宅手当・託児所など |
| `overtime`（6 種） | 残業あり（月の想定時間）・残業なし・1 日 4 時間以内・週 1 日から・短期・土日祝 |
| `experience`（3 種）／`insurance`（4 種） | 数と区分の考え方だけ。ラベルは旧資料内で食い違っていて確定できない |

- 注意: 旧の対応表は 7 ファイルに複製され、**食い違いがあった**（同じコードが別のラベルになる、など）。`overtime` には勤務条件（短期・土日祝）が混ざっていた。コード値の数値は引き継がず、新しく決め直すのがよい。給与（年俸・月給・日給・時給）は新アプリに反映済み。
- 旧には入力の検査がほぼ無かった（必須は職種・雇用形態・法人名・概要・勤務地だけ。金額・時刻・範囲の検査は無し）。新アプリでは検査を足す。

## 5. 3 者の権限の分け方

- 事実: 求職者・求人を出す側・運営の 3 者。求人を出す側は求人登録だけ、運営は申込者一覧・求人一覧・求人登録を持つ。申込者の個人情報は運営だけが見る作りだった（推測: 紹介型の運営方針）。
- 旧の実装は、ログイン後の行き先を変えるだけで、**一覧の URL を直接開くと権限を見ない画面があった**。求人と登録者の紐づけも無かった。実装は参照しない。
- 新アプリに当てると: 求職者と園の 2 者の分離は新アプリの方が堅い。未設計なのは**運営という 3 者目**と、「応募者の個人情報を誰が見られるか」の線引き。

## 参考にしないもの

- 旧方式の認証（エントリー番号を ID にして、仮パスワードを画面とメールで平文通知）。新アプリの登録（3 項目で即ログイン）が上回る。
- 通知メールの文面と署名（実在の連絡先を含む）。種類（登録完了・問い合わせ受付・再設定コード・再設定完了・運営への通知）と、「宛名 → お礼 → 内容 → 次にすること → 期限 → 署名」という型だけが参考になる。新アプリにはメールを送る仕組みが無い。
- 個人情報の取扱いページとプライバシーマーク。架空のサイトに認証マークを載せると虚偽表示になる。
- 検索・求人詳細・画像・会員登録・パスワード再設定・問い合わせ。新アプリが同等以上に作り直した。
- 旧の画面部品（Bootstrap 4・jQuery・Font Awesome の直読み、`component/`、`css/`）。旧ページのどこからも使われていなかった。
